## 2026-08-04 native action-stutter and Scratch purchase repair

boundary, not in Web-only code. Two independent regressions were present:

- Selection-only clicks (item, service, lender, event, travel, and game action)

## 2026-08-04 main-trunk Web startup closure

This section is the authoritative result for the remaining Web blocker and
supersedes the threaded-worker follow-up below. It does not replace the final
human tutorial or owner packaged-build approval.

### Root cause and repair

The cold-start hold occurred before project GDScript: Chrome spent most of the
binding 4x-throttled run compiling and instantiating the 37 MB threaded Godot
WASM. The PCK and WASM transfers were already complete at roughly 1.2 seconds,
so content size, save loading, and network delivery were not the limiting work.
Three threaded cold captures reached ready in 24.175, 23.528, and 23.807
seconds, all over the unchanged 20-second gate.

The accepted export is single-threaded. The earlier single-thread experiment
was unsafe because procedural music called `Thread.start()` and fell back to
long browser-main-thread synthesis. That dependency is removed: the build tool
generates one deterministic 30-second, 22.05 kHz Web bed for each of the 17
procedural archetypes, stores it as compact gzip/BTHA IMA ADPCM, and the runtime
loads it through the existing Web audio bridge. The 17 compressed beds total
about 2.8 MB and retain measured 36-41.5 dB reconstruction SNR.

The menu also used to build every in-run overlay before declaring the start
screen interactive. Web now constructs the run shell in bounded stages behind
the menu; a player who chooses New Run immediately completes any outstanding
stages synchronously before entering play. A real 1280x720 browser click reached
the Apartment and its first Pal prompt normally.

The remaining recurring hitch was slot autoplay. Its action boundary made
three read-only deep copies of the nested machine/reel/bonus state (command,
wager cost, and minimum-return checks), normalized/copied the final machine
again, rebuilt the same UI snapshot twice, and joined presentation refresh to
the resolution frame. Read-only queries now use the canonical stored state,
resolution owns one normalized copy, the already-built lightweight automation
context is reused, and post-commit presentation moves to the following frame.
The moving-reel renderer also omits clipped rows and uses the existing themed
motion treatment until all reels land; settled symbols and outcome mechanics
are unchanged.

## 2026-08-04 Web audio parity repair

The reported Web-only audio depreciation was reproduced and traced to three
separate platform forks: Web SFX were synthesized at 6 kHz instead of the
native 22.05 kHz contract, procedural Web music used a 1 kHz compact bed, and
the JavaScript bridge did not follow the native Master/Music/SFX bus gains.

The repair now uses the shared 22.05 kHz synthesis contract on both platforms.
All 80 Web SFX cues are build-derived from that same synthesizer and delivered
as pre-encoded IMA ADPCM, eliminating first-use synthesis/base64 stalls. Web
authored music uses 22.05 kHz masters derived from the untouched 44.1 kHz WAVs,
with 38.865 dB minimum and 48.658 dB average measured SNR. Lossless container
compression reduces the 2,315,497-byte ADPCM set to 355,119 shipped bytes; the
audio worker performs full validation/decompression off the main thread. The
bridge now decodes both delivery banks, retains the music stem mix, and mirrors
native user bus levels.

Evidence and results:

  outcome probes: PASS, `.tmp/web_audio_fidelity/audio_*_final.json` and the
  harmony probe SHA-256 `159ff00ca23fdd989f63f40d455c02988a743505b9c6cc1c85823de03acb29e2`.

  Web Audio decode errors in the final runtime log.
