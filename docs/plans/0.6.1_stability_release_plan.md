# 0.6.1 stability release plan

Updated 2026-10-26. This is the current release task list. The owner has limited
0.6.1 to stability, bug fixes, issues found through playtesting, and measured
performance improvements. The accepted 0.6 placements remain the baseline;
change them only for a reproduced usability problem or owner feedback.

The official 0.6 baseline is tag `v0.6.0`, source
`a095414b20cdb3570e06b367c621be43e0256109`. Main's subsequent README change
`395990c` does not change the game. Keep the published tag and assets immutable.
The older [deferral inventory](0.6.1_backlog.md) is historical context: its art,
new content, balance redesign, Steam and mobile work is outside this release.

### BTH061-001: Main Menu discards unsettled Coin Pusher actions

First reproduction: shipped Web package, Chromium, 1280×720, standard run
`BTH061-STABILITY-B`, no loadout or edited save. Skip the optional First Night
lessons on a fresh profile, set the seed in Run Setup, then travel normally from
Back Alley to Bar. Open Quarter Falls. At $97, hold/release DROP once: cash
becomes $96. Open Menu immediately, choose Main Menu, then Continue. Cash
returns to $97 and the paid drop is absent. The stored run-state hash is
identical before Drop and after Main Menu:
`fa3cc56f7450bc83c48aa666e2a713b97fe635fef43fa884cace7f4433561c65`.

An independent normal run, `BTH061-STABILITY-D`, reproduced the same $97 →
$96 → $97 rollback at Corner Store's Quarter Falls. It also left the saved
state unchanged after Main Menu. Both cases have retained screenshots and
independently decoded, hash-checked persistence observations.

`FoundationMain._autosave_foundation_run()` returns success without writing
while `foundation_save_ready()` is false. `return_to_main_menu()` calls it
before `_reset_game_surface_runtime_state()` settles the machine, then clears
RunState with no subsequent save. The native close notification also attempts
the save before checkpointing; test that separately. In-game Exit checkpoints
first and must not be assumed identical to Main Menu.

Do not fix this by refunding an already accepted drop, skipping native solver
events, accepting an incomplete snapshot, or disabling simulation. Test paid
actions and resulting payouts/items, not merely a successful Save return value.

### BTH061-002: failed save followed by discarded session

Production lifecycle probe on the identical 0.6 runtime, seed
`BTH061-SAVE-FAILURE`. Save a normal $100 start. Make only the probe's isolated
save directory unwritable by replacing that directory with a regular file,
retaining the original directory. Perform normal production travel to Bar:
cash becomes $97. Request Main Menu. The forced save reports
`temporary_open_failed`, error 12, and “Autosave failed. Retry from Run Menu or
after another action.” Nevertheless RunState is cleared. Restore the original
directory and Continue: cash is $100, so the live trip was lost.

This is a fault-injection reproduction, not a claim that ordinary healthy
storage fails. Recovery must keep the live state accessible on failure and
honor the result at the navigation caller. Keep atomic-write/backup guarantees.

## Testing and coordination

The release assessor runs its own tests. The other worker independently owns
its 0.6.1 playtesting and fixes; neither worker's assertion substitutes for the
assessor's verification. Share coherent commits and reproductions, avoiding
overlapping fixes to the same root cause. Preserve useful in-flight work before
syncing to main; selectively carry replay-tool fixes only when needed for real
testing. A hidden-chip validator already landed with the release; do not
duplicate it. Review complete state changes before refreshing expected hashes.

Existing release checks remain useful evidence. Repeat them when a fix affects
their behavior or at the final candidate, rather than restarting the old
closure process after every documentation or tooling edit. Do not adopt an
old multi-hour certification procedure merely because it remains in a TODO.

For each new finding record: ID; source/build; platform; seed and starting
profile; shortest steps; expected/actual result; evidence; severity; owner;
fix commit; failing-seed retest; independent-seed retest; remaining limits.
Unknown fields remain unknown. Owner reports may start with only a description
and screenshot; the assessor fills in the reproduction details.

## Release decision

Before 0.6.1 ships, resolve confirmed crashes, lost/duplicated progress or money,
broken required progression and critical save incompatibilities. Give every
other reproduced finding a fix or an explicit recorded disposition. Planned
coverage is not a pass, and historical failures are not current defects until
reproduced. Performance claims require measurements, with live animation and
real game progress alongside timing. Keep one concise record of what actually
changed, why it helps players, and how the fixed build was checked.

[2026-10-18 assessment](../reports/0.6_stability_assessment_2026-10-18.md).
