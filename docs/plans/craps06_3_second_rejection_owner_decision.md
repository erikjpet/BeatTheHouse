## 2. What the rejected heads establish and do not establish

### Core first rejection: `f5a30b19`

The first candidate introduced a five-profile `game_ritual/1` package, the bet
matrix and shared-assembly manifest, Craps module changes, and a row-local depth
contract. It was rejected because the profiles were declarations rather than
registered/consumed behavior; the gesture vector did not drive tactile travel,
bounce, separation or offer/return; and token-level proof did not execute the
required lifecycle, platform, environment and hostile behavior. The manifest
also improperly assigned implementation work to the Integrator. Presentation
could remain in `aiming_throw`, and two exact registered row-facing assertions
were red.

### Core second rejection: `e8cc589e`

The remediation materially improved the tactile projection, hostile in-motion
input rejection, accounting/control surface and row-local proof. Those changes
remain review evidence, not an accepted slice. The second rejection found:

- the real UI still returns to `aiming_throw` and skips the offered phase for
  non-pointer input modes;
- the five authored sequences remain unconsumed declarations rather than five
  executed production sequences;
- the dense capture truncates eight bets to five and omits complete available,
  new-stake, at-risk, payout, returned-stake and per-bet accounting evidence;
- the shared manifest still assigns implementation to the Integrator; and
- Web parity evidence is absent.

All other requirements in the full prompt remain binding unless an owner option
explicitly changes them. The row-local PASS, visual capture and million-roll
results recorded in `8ad3dd11` do not waive the missing production composition
or platform proof.

### Environment first rejection: `37353057`

The first environment slice added exactly:

- `data/games/rituals/craps06_3_environment_bindings.json`;
- `scripts/core/craps06_3_environment_binding.gd`; and
- `scripts/tests/foundation/craps06_3_environment_integration_contract.gd`.

It was rejected because an unkeyed self-hash was treated as producer
authentication; the caller selected an unsealed profile; response application
accepted arbitrary registry-valid operations/full inventory; and context/table
ownership was not proven. The slice did not authorize edits to frozen env06_6,
shared catalogs, shared routing, crew/world models, the board or main.

### Environment second rejection: `872d09a9`

The remediation bound responses to committed receipts, table/context facts,
safe-boundary release, exact catalog responses and restricted declared targets.
It remains rejected because the immutable package/profile selection is not
rooted in the committed table state. A same-domain Craps producer can commit a
transaction whose fact payload relabels the ritual profile and then ask the
binding to route that relabeled profile. The proof rejects cross-domain and
foreign-profile replay, but does not prove a fully committed same-domain
package/profile relabel fails closed. Thus profile selection is still
producer-asserted rather than table/committed-state-authoritative.

The environment slice cannot land independently as authoritative integration.
It also does not perform the shared registration, safe-boundary routing or
production composition required to make the five profiles live.
