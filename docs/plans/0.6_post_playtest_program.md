# Beat the House 0.6 Post-Playtest Completion Program

Status: **PARKED - DESIGN ONLY.** This document does not open the polish pass,
authorize a task, or perform release work.

Prepared by: `polish06_0`

This program gives the second half of 0.6 a shape before the owner's playtest
findings exist. It begins only after the owner finishes that playtest, accepts
its capture, and explicitly declares the polish pass open. Until then, every
new row below remains `PARKED` and no agent may claim, schedule, or partially
execute it.

This document complements the roadmap, active board, remaining-work program,
`playtest06_2` capture contract, `balance06_1` report and harness, and the
existing `voice06_1` and `release06_1` prompts. It does not replace locked
design or grant release authority.

## Non-negotiable authority boundaries

1. **The owner opens the pass.** A completed playtest or a populated capture
   file is not permission to start. The owner must explicitly declare the
   polish pass open.
2. **No task self-unparks.** The board coordinator changes an eligible row from
   `PARKED` to `TODO` only after its conditions below are evidenced. A worker
   may claim only a `TODO` row.
3. **The owner decides design.** An agent can identify a note as a possible
   design objection, assemble evidence and record an unresolved roadmap
   decision. It cannot reinterpret locked design, select a new direction, or
   turn that note into an implementation row without the owner's recorded
   decision.
4. **The owner decides what blocks 0.6.** Severity is an evidence-based triage
   recommendation. Only the owner assigns the final `BLOCK_0.6` or
   `DEFER_0.7` disposition, including for P0/P1 findings.
5. **Release activity belongs only to `release06_1`.** No other row may bump a
   version, build or package a release, create a tag, upload, publish, or claim
   an owner release gate. Source approval, packaged-artifact approval and
   publish/upload authorization are separate explicit owner decisions.
6. **The program stops at a clean handoff between rows.** Historical green
   reports prove only their recorded source. Every downstream row identifies
   and verifies the exact source it consumes.

## Inputs the owner must have before opening the pass

- `playtest06_1` is complete on a named, committed build and the owner has
  finished the intended playtest sessions.
- The capture produced by the `playtest06_2` contract contains the raw notes,
  build, seed, platform, route/session and available evidence. Missing fields
  stay visibly unknown; agents do not fill them with guesses.
- `balance06_1` has delivered its committed harness, per-playstyle baseline
  distributions, ranked findings and ranked proposals.
- The playtest handoff identifies deliberate absences and known roughness so
  triage does not mislabel unbuilt or owner-accepted work as a defect.
- The board and roadmap identify the exact accepted pre-playtest source.

If any input is missing, `triage06_1` stays parked. The owner may still add
notes to the raw capture; that is not execution of this program.

## Finding triage protocol

### Preserve the observation

`triage06_1` first copies each owner note into a normalized ledger without
rewriting its meaning. Each entry keeps:

- finding id and the owner's original wording;
- observed behavior, expected behavior and location/surface;
- build commit, platform, save provenance, named seed and playtest session;
- shortest known reproduction and attached capture/log/save evidence;
- frequency and consequence;
- proposed class, severity, owning system and gate analysis;
- owner disposition and, when applicable, roadmap decision id or `fix06_*`
  row id.

Unknown reproduction fields are recorded as `UNKNOWN`. A note is never dropped
because it is incomplete.

### Classification that prevents agent-side redesign

| Class | Test | Route |
| --- | --- | --- |
| Defect | Observed behavior violates an existing accepted rule, contract, invariant or explicit expected behavior. | Draft a `fix06_*` prompt, including a regression/gate repair. It becomes claimable only after owner disposition and board coordination. |
| Design objection | The implementation may match the current contract, but the owner objects to the rule, direction, feel or intended experience. | Record a `PENDING OWNER` roadmap decision. Do not create an implementation row. |
| Unclear | Available evidence cannot determine whether the expectation is existing or new. | Treat as a design objection until the owner resolves it. No implementation row. |

This is enforced structurally: a fix derived from a design objection must cite
an owner-approved roadmap decision id and the approved outcome. Without that
field, the fix prompt is invalid and the board coordinator must not add or
unpark it. Agents may gather a minimal reproduction while a decision is
pending, but may not change product code, content, rules or tuning.

### Severity and owner disposition

| Severity | Evidence-based meaning | Normal recommendation |
| --- | --- | --- |
| P0 | Data loss/corruption, security or privacy exposure, destructive migration, or a candidate that cannot launch or be recovered. | `BLOCK_0.6` |
| P1 | A promised core path is wrong or unavailable; deterministic, money-conservation, save, platform, or release-critical behavior is broken; no reasonable workaround exists. | `BLOCK_0.6` |
| P2 | Material functional or experience failure with bounded scope or a reliable workaround. | Owner chooses block or defer. |
| P3 | Non-functional polish, minor presentation or low-impact edge case. | Usually propose `DEFER_0.7`; owner decides. |

Severity does not make the shipping decision automatically. Every ledger entry
must carry exactly one owner disposition: `BLOCK_0.6`, `DEFER_0.7`,
`DESIGN_DECISION_REQUIRED`, or `NOT_A_FINDING`, with the date and the owner's
recorded wording or reference. A deferred item remains in the roadmap with its
evidence and target; it is not deleted from the ledger.

### A defect is also a gate defect

Every `fix06_*` prompt must name the gate that should have caught the behavior,
why it did not, and the permanent negative/regression case that will fail
before the repair and pass after it. If no automated gate reasonably could have
caught it, the prompt says why and adds the smallest durable manual or
instrumented check. `No gate` without an explanation is not acceptable.

The complete defect-row template lives in
`docs/todo/triage06_1_post_playtest_findings_prompt.md`.

## Ordered execution and unpark conditions

```text
owner closes playtest and opens polish
  -> triage06_1
  -> owner records design decisions and 0.6/defer dispositions
  -> owner-required fix06_* rows
  -> balance06_2
  -> cleanup06_1
  -> voice06_1
  -> release06_1
```

### 1. Triage

Unpark `triage06_1` only when all opening inputs are present and the owner has
opened polish. It finishes when every raw note is represented exactly once,
every design objection is linked to an owner decision state, every defect has
a gate analysis and draft fix row, and every finding has an owner disposition.

### 2. Fixes

The board coordinator adds only the owner-authorized `fix06_*` rows. Fixes may
run in parallel when their file ownership and behavioral dependencies are
disjoint. Shared systems, shared data files, migration formats and a common
failed gate serialize the affected rows. Each fix repairs the product defect
and the escaped gate in the same acceptance contract.

No downstream row begins while any `BLOCK_0.6` fix is open. A `DEFER_0.7`
finding is allowed to remain only with the owner's dated disposition and a
roadmap target.

### 3. Balance tuning

Unpark `balance06_2` after all owner-required fixes land, so it measures the
game the owner actually approved rather than tuning around a defect. This row
is the post-playtest authority to apply tuning values. It supersedes the old
balance-application language in `release06_1` Task section 1: `release06_1`
re-runs and verifies the final distributions but does not perform a second
tuning pass.

Every changed value must be supported by both a ranked `balance06_1` proposal
and a specific accepted playtest felt-experience finding. The committed
`balance06_1` harness runs before and after with identical source inputs,
playstyles, seeds and action policies. The report includes distributions and
tails, not only averages. Presentation, prose, content, rules and structural
logic are outside this row.

### 4. Cleanup

Unpark `cleanup06_1` only after tuning and all blocking fixes are accepted.
Cleanup removes proven leftovers, not merely unfamiliar files. It traces
dynamic Godot loads, manifests, scenes, data consumers, generated-tool callers
and documentation citations before deletion, with one logical class per
commit and focused gates after each.

`.tmp/`, `.tools/`, ignored paths and untracked directories are owner property
in this project. They are deliberately retained even when large or apparently
generated. The cleanup row must not delete, move, stage or repurpose them. It
also preserves historical documents unless the board protocol explicitly
archives them; it reconciles current claims without erasing history.

### 5. Voice

Unpark `voice06_1` only after cleanup has landed and the owner confirms that
all non-deferred content and player-visible strings are final. This is why the
voice pass cannot overlap any earlier row. Its existing string-only and hidden-
information rules remain binding.

### 6. Release

Unpark `release06_1` last, only after the owner declares the polish pass
complete and every dependency in the table is accepted on one clean source.
It consumes the release templates below, performs exact-source verification,
and stops separately for final source approval, packaged-artifact approval and
publish/upload authorization. It is the only row allowed to package, version,
tag or publish.

## Parallelism without accidental serialization

- Independent `fix06_*` rows may run concurrently after triage and owner
  disposition. Their ownership map must prove that they do not share files,
  migrations, save schemas, gate fixtures or coupled behavior.
- Evidence collection for a pending owner design decision may run beside an
  unrelated authorized defect fix, but implementation of that decision cannot.
- `balance06_2`, `cleanup06_1` and `voice06_1` are deliberately serial. Each
  changes the exact input of the next stage.
- Inside `cleanup06_1`, read-only inventories can be gathered in parallel;
  deletions and documentation reconciliation land only after the inventories
  are combined against one head.
- Inside `release06_1`, factual copy, screenshot and trailer-shot inventories
  may be assembled in parallel after the source candidate is frozen. Candidate
  verification, versioning, packaging, the three owner gates, tagging and
  publication remain serialized. A source change invalidates affected evidence
  and every artifact built from it.

## Version and hotfix policy

0.6 ships as **`0.6.0`**. It is the next public minor feature release after
the shipped 0.5 line (currently 0.5.1). The unpublished 0.4.0 release candidate
is historical evidence that a tag or version stamp is not proof of publication;
it does not consume or rename 0.6.

`release06_1` changes the identity only after the final source candidate is
otherwise ready and before that candidate's complete exact-source matrix. The
version must agree across `project.godot`, every supported export preset, UI
render, README, CHANGELOG, artifact names, public copy and tag. If the owner
chooses a different public version before final source approval, the owner
records that decision and the entire identity is updated consistently; an
agent never infers a version from repository lag.

If a defect is found after `0.6.0` is published, the patch line is `0.6.1`,
then `0.6.2`, and so on:

1. branch from the exact published tag;
2. accept only the smallest defect and gate repair - no features, design
   redirects or opportunistic balance changes;
3. preserve save compatibility and add a reproduction/negative control;
4. rerun affected gates plus release validation, determinism, platform smoke,
   migration and artifact verification on the new exact source;
5. obtain fresh source, package and publish authorization;
6. build new artifacts and create an annotated `v0.6.x` tag at their exact
   source; never move or reuse `v0.6.0`.

A fix that changes design, content scope, save contracts broadly or economic
rules belongs to the planned 0.7 line unless the owner explicitly reopens 0.6.
