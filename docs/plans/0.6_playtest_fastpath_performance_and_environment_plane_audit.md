## Outcome

The playtest build is ready for packaging. The complete native performance
probe passed 51 observations with all 11 games represented, all ten
turn-resolution paths under their budgets, live idle counters, and no gameplay
full-state snapshot fallbacks. A separate pointer audit reached all 632
generated controls at both normal and small-screen hit sizes with no blocked,
off-board, fully occluded, incorrectly dispatched, or external targets.

The owner-reported roughly 20-second wait at startup was not reproduced after
the fixes. The final native menu contract reached a completed prewarm in
4,091 ms and opened a prewarmed run in 636 ms. The last authorized cold Web
fastpath measurement reached ready in 4,295 ms and opened the Corner Store in
508.47 ms.

The environment/scenario split-layer defect is also closed. Static room
fixtures, runtime-only controls such as the Numbers book, and scenario props
now share one placement plane. Scenario semantics may change an existing
object's state or presentation, but they cannot move its generated room
location. New scenario objects are placed around the complete visible room
inventory. The production Punchline route selected every available object,
reported zero overlaps in both rooms and both hit-size modes, saved/continued
in each room, and revisited both rooms successfully.

No odds, payouts, RNG streams, stakes, debt terms, game rules, progression,
timing windows, or authored outcomes were changed.

## Measurement method

- Host: Windows 10, Intel Core i9-9900K (8 cores / 16 logical processors),
  63.9 GiB RAM.
- Engine: Godot 4.6 stable, headless. Native Coin Pusher measurements required
  the shipped `native_v3` solver binary and recorded its SHA-256.
- Native final probe: two deterministic runs, 60 frames per surface, 12 resolve
  samples per game, plus explicit practice coverage where generated runs did
  not contain every game.
- Web fastpath: Chrome 152, 1280x720, cold cache, CPU throttle 1, 45 idle frames,
  60 active frames, 20-second memory windows, 65 scenarios.
- Environment stress: 20 deterministic runs, six visits per run, 120 generated
  rooms and 100 travel transitions.
- Player-route tests: production `main.tscn`, exact rendered semantic IDs, and
  real `Viewport.push_input(InputEventMouseButton)` events. Direct host action
  calls and injected fixture rooms were forbidden for this evidence.
- Pointer reachability: every hit region emitted by every shipped game surface,
  sampled at normal and expanded small-screen sizes.

The final native measurements were taken without another performance workload
running. Timings are development-machine evidence, not portable hardware
guarantees.

## Optimizations made

### Startup and loading

- Moved expensive menu prewarming into bounded frame slices so the menu becomes
  responsive while immutable data warms in the background.
- Kept Web-only run UI dependencies deferred until Play is requested. The
  startup loader cannot synchronously pull the full gameplay script graph into
  the initial page load.
- Reused validated immutable content and configuration data rather than parsing
  or copying it again for each game/session.

Final native evidence: prewarm 4,091 ms, worst menu frame 38.838 ms, prewarmed
Play 636 ms. Cold Web fastpath evidence at `1964c7dc`: ready 4,295 ms against
20,000 ms and Corner Store open 508.47 ms against 1,200 ms.

### Game rendering and action paths

- Removed repeated temporary packed-array creation and derived-geometry work
  from Bar Dice, Blackjack, Craps, Roulette, Pull Tabs, and Crew Draw Poker draw
  paths.
- Kept Baccarat's realtime surface patch lightweight and removed a second
  redundant refresh path.
- Replaced full game-state snapshots with narrow, read-only runtime status on
  liveness and watchdog paths. The final probe recorded zero full snapshots for
  all measured gameplay surfaces.
- Avoided rebuilding UI state when the host already owns an exact result patch,
  and skipped dormant work when a surface is hidden or an animation is inactive.
- Preserved every live animation counter. The synthetic negative liveness test
  still fails when redraws are suppressed, while the restored path measured 49
  advances and passed.

The broad baseline at `bf398237` and final probe use different sample shapes,
so they are not treated as a statistical A/B test. They are directionally
consistent: Slot resolve p95 was 3.039 ms in the 48-sample baseline and 1.637 ms
in the final 12-sample verification; Blackjack and Baccarat remained within
their tighter budgets throughout.

### Scenario, save, and environment work

- Memoized successful scenario-schema proofs with a hard 256-entry bound.
  Production validation covered all 1,485 scenario/environment pairs, observed
  55 intended reuse hits, and retained only 256 entries.
- Kept no-sequence catalog receipts process-local. They no longer enter the
  living-world seed or serialized saves, while the runtime still reuses the
  trusted negative lookup.
- Stopped cloning inactive game states when a sealed host action changes only
  the current game.
- Removed redundant scenario projection/finalization work and eliminated
  gameplay hot-path deep copies where the caller already holds immutable
  authority.
- Generated stable room rectangles for Numbers fixtures. The runtime controller
  supplies other live-only controls as bounded, read-only occupancy records;
  those records affect placement but never gain scenario action authority.
- Existing machine, item, event, service, lender, and travel rectangles remain
  exactly owned by the environment generator. Scenario resolution can only
  displace newly introduced scenario props.
- Added an 8-pixel deterministic fallback for unusually dense rooms only after
  the existing cheap offsets and 16-pixel grid fail. Its expensive sorted
  candidate list has an eight-entry LRU bound. A 20-call microprobe reduced
  repeated candidate generation from 13,016.4 microseconds per call to 663.9
  microseconds average without changing candidate order or selected geometry.
- Cleared the canvas's presentation-only selection at travel boundaries so a
  destination no longer inherits the source room's Leave focus/zoom.
