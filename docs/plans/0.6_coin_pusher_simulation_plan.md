## 1. Assessment of the 3D proposal

An external analysis proposed a 3D rebuild: `Node3D` machine scenes,
pooled `RigidBody3D` coins, hybrid physics where the existing model
constrains payouts, at 7–18 months depending on staffing. The
engineering breakdown in that analysis is competent and its component
list is broadly correct. Three of its conclusions do not survive
contact with this codebase.

### 1.1 The hybrid recommendation is the same defect, better dressed

The proposal recommends physics that *runs* while the existing coarse
model *decides* payouts, with "a reconciliation layer [that] gently
resolves unacceptable divergence."

That is the exact failure the owner already rejected. If a coin
visibly tips over the ledge and lands in the tray, and a reconciler
then decides the payout was something else, the machine is lying in
the most visible way a machine can lie. Players read coin pushers by
watching the pile; a simulation that does not determine the outcome
will feel *more* fraudulent than honest abstraction, not less.

**The simulation must be authoritative.** What crosses the payout
edge is what pays. Anything else reproduces the "loosely based on a
coin pusher" verdict with a bigger budget.

### 1.2 Determinism is solvable by owning the solver, not by reconciling

The analysis is correct that Godot's built-in physics will not
reproduce identically across Windows, Web, and mobile, and correct
that this collides with seeded runs, reproducible tests, and save
integrity — all hard rules in this project.

The conclusion drawn is wrong. The answer is not to let
non-deterministic physics run and paper over drift; it is to **own a
small deterministic solver**. A coin pusher does not need general
rigid-body dynamics. It needs discs on a plane, stacking in shallow
layers, a sweeping plate, and falls between two levels. That is a
narrow, well-understood simulation that fits in a fixed-timestep,
fixed-point, seeded solver of moderate size — fully deterministic by
construction, on every platform, forever.

### 1.3 3D is a project-level commitment, and it is not what produces the feel

Verified state of this repository:

- `renderer/rendering_method="mobile"`, `.windows="gl_compatibility"`
- zero `.glb/.gltf/.obj/.fbx` assets
- zero `Node3D`, `RigidBody3D`, or `MeshInstance3D` usage anywhere
- every game surface is GDScript-drawn 2D
- surface draw budget `MAX_SURFACE_DRAW_P95_MS = 5.0`, idle `1.5`,
  living-floor frame p95 `16.0` — and this project has a documented
  history of surfaces blowing frame budget

So this is not "add 3D to the pusher." It is "make this a 3D-capable
project, for one machine type that spawns in tier-1 shops," with a
new renderer path, a new asset pipeline, new lighting and camera
systems, and a second physics stack — inside a codebase whose 2D
surfaces already fight for 5ms.

And the feel does not come from dimensionality. It comes from
**authoritative simulation plus layered audio**. The analysis itself
concedes this: "excellent physics with weak audio usually feels
fake." A 2.5D pusher with real coins, real stacking, real cascades,
and excellent sound reads as a coin pusher. A 3D pusher with
reconciled payouts does not.

### 1.4 What the analysis gets right

- Coin pushers are unusually demanding: dense persistent contact
  between many thin bodies is the hard part, not the rendering.
- Prototype first, with a real performance target on the weakest
  supported target, before committing the full system.
- Audio is load-bearing for credibility.
- Coin pooling, sleeping, active-subset simulation, settle detection,
  and recovery from wedged/exploded states are all mandatory.

Those four points are adopted wholesale below.

## 2. Recommendation

**Build an authoritative, deterministic 2.5D coin simulation with a
presentation layer held behind a clean boundary.**

Two properties make this the right call:

1. **Honesty.** The sim decides payouts. No reconciliation layer.
2. **Reversibility.** Simulation state is published as a pure,
   renderer-agnostic snapshot (coin positions, layers, motion,
   events). The 2.5D renderer consumes that snapshot. A 3D renderer
   would consume *the same snapshot*. If the owner later wants 3D,
   it becomes a **presentation project on a proven machine** — not a
   gameplay rewrite, and not a decision that has to be made now.

That boundary is the single most valuable architectural decision in
this plan, and it costs almost nothing to honor from the start.

### Geometry model

A coin pusher is not a general 3D problem. Model it as:

- **A plane** (`x` lateral, `y` depth) on which coins are discs.
- **Shallow integer layers** (`z` ≈ 0–3) for stacking. Coins rest on
  the field or on the coins beneath them; layer occupancy is what
  makes piles lean and topple.
- **Two tiers**: an upper shelf and a lower field. Coins pushed off
  the upper shelf **fall to the lower field**, landing among and
  disturbing what is there. Coins pushed off the lower field fall to
  the **tray** (payout) or the **gutters** (loss).
- **A sweeping plate** with a physical cycle that bulldozes contact.

Emergent behavior required: uneven piles, leaning stacks, topples,
cascades from a single landing, overhangs that form because coins are
physically there, and nudges that shove a real pile.

### Solver requirements

- Fixed timestep, decoupled from frame rate, interpolated for render.
- Fixed-point or integer arithmetic — no floats in state that affects
  outcomes.
- Seeded; identical seed + identical input sequence reproduces the
  identical pile, coin for coin, on Windows and Web.
- Impulse/position-based contact resolution with a fixed iteration
  count (iteration count is part of the deterministic contract).
- Spatial-hash broadphase.
- Aggressive sleeping: settled coins cost nothing until disturbed.
- Recovery: no tunneling, no wedged coins, no exploding stacks — and
  explicit detection plus deterministic correction if they occur.
- Settle detection before an outcome is recorded.

### Performance strategy

The pile is mostly static. Coins settle; only the sweep and fresh
drops move anything. Budget accordingly:

- Hard cap on coins per cabinet (start at 200; lower it if needed).
- Active set typically well under 50 bodies; everything else asleep.
- Step only while the machine is active; idle attract animates
  cheaply and must still satisfy the liveness counter-gate.
- Render coins through batched drawing, not per-coin node overhead.
- Budgets are non-negotiable: surface draw p95 ≤ 5.0ms, idle ≤ the
  animated idle budget with its liveness counter, frame p95 ≤ 16.0ms.

**If the budget cannot be met, the correct response is to lower the
coin cap and report the number — never to re-abstract the pile.**
That rule exists because re-abstraction is precisely how the first
implementation failed.

## 3. What gets kept

The rejected work was the *simulation core*, not the surrounding
system. These landed correctly and carry forward unchanged:

- Three variation identities: Quarter Falls, Jackpot Ridge, The Vault
  Drop, with per-node variation seeding and distribution.
- The universal nudge system: force × direction × timing, hidden
  per-node alarm tolerance modified by venue security, scenario
  overrides and the swept-window, and the tell ladder (rock, chirp,
  attendant glance).
- The alarm contract: hard alarm locks that machine for the night,
  significant heat spike, node memory — and **never forces the player
  out of the environment** (owner decision 23). Smash-and-grab
  remains viable.
- Economy integration, heat, cheat items (`cold_quarters`,
  `coin_return_shim`, `weighted_keyring`, Mags dampener,
  `xray_glasses`), pile persistence in node snapshots, pusher-pile
  rumor facts, venue placement and scenario access effects.

Nudges become *better* on a real sim: a nudge now shoves actual
coins, which is what makes the mechanic honest.

## 4. Per-variation sub-games

Each variation carries a genuinely distinct bonus system — a player
must describe them as three different machines, not one machine with
three number sets.

**Quarter Falls — the pure pusher.** Bonus layer is **prize riders**:
physical objects sitting *in* the pile (chip stacks, a watch, a
ticket roll, scenario-seeded real inventory items) simulated
alongside the coins, pushed and falling with them. Skill is reading
physical pile state and choosing where to feed.

**Jackpot Ridge — the sequencing pusher.** **Feature pucks** are
physical bodies in the pile: multipliers, shelf locks, dud jams. They
must be physically worked loose and pushed off to bank. The sub-game
is a physics-puzzle: which puck to free first and what the pile does
when you do. Ridge Run cascade on three multipliers banked in one
sweep cycle.

**The Vault Drop — the progressive pusher.** **Key fragments** in the
pile bank toward a vault round: pick-and-reveal behind a playfield
door, paying from a **town-fed progressive meter** (TownState-driven,
growing on action boundaries, faster in crowded scenarios). Cells
hold cash, items, fragment refunds, and an honest RESET cell with
documented odds. `xray_glasses` peeks one cell.

---

## 5. Audio is a first-class deliverable, not polish

Credibility is carried by sound at least as much as by physics:
coin-on-coin impacts that vary with stack depth, sliding under the
plate, the motor loop tracking the sweep, the tray cascade, the
gutter's flat swallow, cabinet shake under a nudge, the chirp ladder
before an alarm. Audio ships **with** the presentation phase, not
after it.

## 6. Phased execution with kill criteria

### Status correction (2026-08-16): Phases 0–1 are largely already done

This plan was drafted assuming the rebuild had not started. It had.
`rework06_2` (in flight on `codex/rework06-2`) already contains
`scripts/games/coin_pusher/coin_pusher_solver.gd` — a **real
fixed-point discrete-body solver**: 60 Hz fixed step, integer
coordinates, two floor tiers with gravity and drag, spatial-hash
collision resolution, `_resolve_supports` for stacking, sleeping,
`body_views` as a renderer-agnostic snapshot, `canonical_digest` for
determinism, height-grid migration, and a **cross-platform export
parity runner**. The surface consumes `body_views` and audio hooks
exist.

That is precisely the architecture this plan recommends, including
the snapshot boundary that keeps 3D a later rendering choice. The
feasibility question Phase 0 existed to answer has effectively been
answered by construction.

**Therefore:** `pusher06_0` and `pusher06_1` are retained as written
but repositioned — `pusher06_0` becomes an optional *measurement and
hardening* pass rather than a go/no-go gate, and `pusher06_1`'s
substance is delivered by `rework06_2`. Do not re-run them against
work that already exists; verify `rework06_2` by code first and claim
only what is genuinely missing.

| Phase | Prompt | Deliverable | Status |
| --- | --- | --- | --- |
| 0 | `pusher06_0` | Measurement/hardening: coin cap, frame/solver/render p95, pathology counts, Windows-vs-Web parity, adversarial + long-run cases | Optional — claim only if `rework06_2` did not measure these rigorously |
| 1 | `pusher06_1` | Authoritative solver + Quarter Falls on the kept systems | **Largely delivered by `rework06_2`** — use as an acceptance checklist |
| 2 | `pusher06_2` | Presentation + audio depth: the feel pass | Genuinely remaining |
| 3 | `pusher06_3` | Ridge + Vault as three *distinct* machines | Partially — reconciled to the solver; distinctness unproven |
| 4 | `pusher06_4` | Venue integration, persistence at run scale, town wiring | Genuinely remaining |
| 5 | *(owner-gated, not authored)* | Optional 3D presentation upgrade against the same snapshot boundary | Owner decision |

The lesson recorded for future planning: **check for in-flight work
before authoring a phase plan.** This document was written one wave
behind reality and had to be corrected.

### Honest effort estimate

For the recommended 2.5D authoritative path: roughly **11–17 weeks of
focused agent work**, poorly parallelizable because it is one system
with a long serial spine (solver → feel → variations → integration).

For the full 3D path as proposed: the external analysis's 7–18 months
is, if anything, optimistic for this codebase, because it omits the
cost of making a 2D-only project 3D-capable at all.

The recommended path reaches most of the felt result for a fraction
of the cost, and leaves the 3D door genuinely open rather than
theoretically open.

## 7. Relationship to 0.6

This plan is larger than the remaining 0.6 content work. The owner
should decide explicitly whether the coin pusher rebuild:

- **(a)** runs inside 0.6, delaying the playtest handoff;
- **(b)** runs after the playtest handoff as its own project, with
  0.6 shipping the pushers disabled or de-scoped to fewer venues; or
- **(c)** runs in parallel on its own branch, merging when Phase 2
  proves the feel.

**Recommendation: (c), gated on Phase 0.** The Phase 0 lab is cheap,
answers the feasibility question with measurements, and does not
block Wave D. If Phase 0 returns GO, the rebuild proceeds on its own
branch while the crew path continues. If it returns NO-GO, the owner
has real numbers instead of an estimate, and the fallback is a
de-scoped pusher rather than a stalled update.
